# Survey 2026-09: what sudo-less can install

A random sample of Debian packages, checked by prediction and by real
installation, to measure sudo-less by Debian section. It is the evidence
behind [`design.md`](design.md) and [`standard.md`](standard.md), and the
baseline that later versions are compared against (criterion 2 in the
README).

Raw data: [`survey-2026-09/static.tsv`](survey-2026-09/static.tsv) (696
packages, prediction) and [`survey-2026-09/install.tsv`](survey-2026-09/install.tsv)
(129 packages, real installation).

## Method

- **Archive:** Debian sid, amd64, index of 2026-09-23: 77 228 packages in 58
  sections.
- **Host:** Debian forky/sid, kernel 7.1, apt 2.8.1 + dpkg 1.22.6 from the
  sudo-less prebuilt (Termux patch set).
- **Sample:** 12 packages per section, drawn at random (seed `20260923`),
  leaving out transitional and dummy packages, the `required` / `important`
  / `standard` packages of a base install, and packages larger than 30 MB:
  **696 packages**.
- **Prediction:** `scripts/catalog/check-package.sh --runtime` on all 696:
  maintainer scripts and file lists of the downloaded `.deb`, nothing
  installed.
- **Real installation:** the first 3 packages of each section proposed as
  in scope (43 sections, **129 packages**), each installed with
  `apt-get install --no-install-recommends` in the `sl-fresh` account
  ([`../dev/dsb/`](../dev/dsb/)): a fresh account with only the sudo-less
  prebuilt. **Every package starts from the same clean prefix**, so one
  broken package cannot affect the next. Each executable the package ships
  is then run with `--version` (else `--help`), directly and, failing that,
  through `tools/prefix-run.sh`.
- Two packages failed on the network and are left out: **127 valid**.

## Results

### Real installation (127 packages, 43 sections in scope)

| outcome | packages | share |
|---|---|---|
| **installed** | 80 | **63 %** |
| blocked by **version skew** with the host | 30 | 24 % |
| blocked by a **maintainer script** | 17 | 13 % |

Of the 80 installed, 48 ship no executable (libraries, documentation,
fonts, data) and 1 was already on the system. Of the 31 with executables:
7 run directly, 7 through the overlay, 5 partly, 12 fail. About half of the
12 are the test's fault (no
`--version`, needs a display or a terminal); the rest fail for real, mostly
`error while loading shared libraries` (`zipcmp`, `scotch-64`,
`davegnukem`, `ruby-money`), not yet explained.

### Prediction (516 packages in scope)

| predicted mechanism | share |
|---|---|
| none (runs directly) | 73 % |
| overlay | 17 % |
| environment | 4 % |
| out of reach | 4 % |

Of the 123 packages predicted to need the overlay (all sections), 119 are
for paths compiled into files (mostly `/usr/lib`, `/usr/share`), 4 for a
shebang only. The prediction does not see version skew, so it is more
optimistic than real installation.

## Findings

### 1. Version skew with the host is the largest blocker (24 %)

A newer package in the archive needs a newer system library than the host
has, for example `libqt6core6t64 (>= 6.11)` against 6.10 installed. The host
simply is not upgraded, and sudo-less may not upgrade system packages. This
is a feature of a rolling suite: on Debian stable, the archive and the host
agree and the skew is close to zero. A two-layer package database (patch B)
would not fix it. What helps: the prefix following the host's suite, the
admin keeping the host upgraded, and stage 2 saying "needs the admin to
upgrade X" instead of apt's "held broken packages".

### 2. Maintainer script failures (13 %) fall into known classes

| cause | packages | answer in the design |
|---|---|---|
| writes to `/etc` or `/var/log` (`/etc/.java`, `/etc/freetds`, `/var/log/xen`) | 4 | `DPKG_ROOT` and seeded directories, or refused in stage 2 |
| a file the script expects is missing (`$PREFIX/etc/shells`; `add-shell` already honours `DPKG_ROOT`) | 1 | seed it |
| a helper not available (`update-menus`, `update-xmlcatalog`) | 2 | shims |
| calls the package's own binary by absolute path (`ghc.postinst` runs `/usr/bin/ghc`, which is in the prefix) | 2 | a new class: shim or run the script under the overlay |
| a dependency's trigger or `postinst` (`tex-common`, `libreoffice-common`, `libgdiplus`) | 4 | to study one by one |
| unpacking a setuid helper (`spice-client-glib-usb-acl-helper`) | 1 | patch C (prefix hygiene) |
| a service or system user (`log2ram`, `wmbusmeters`, `ceilometer`) | 3 | admin scope: refused in stage 2 |

### 3. One broken package wedges the whole prefix

In a first run without isolation, `ghc`'s `postinst` failed, and every later
install tried to configure it again and failed too; `yash`'s `postrm` then
failed as well, so it could not be removed even with `--force-all`. 117 of
141 results were this cascade, not the packages. A user has no way out
today: hence stage 2 stopping unsafe scripts before dpkg runs, and a
recovery command.

### 4. A fresh account does not work at once

Found while preparing the survey, all in the prebuilt:

- `apt-get update` fails: current Debian ships `sqv`, not `gpgv`, and apt
  2.8.1 knows only `gpgv`;
- `dpkg-maintscript-helper` looks for its helpers in the build machine's
  `/root/.local/share/dpkg`, and dpkg logs to `/var/log/dpkg.log`;
- `tools/` (`prefix-run.sh`, `deb2home.sh`) is not in the prebuilt.

## What changes because of it

- Scope by section ([`standard.md`](standard.md)): the "admin" sections
  predict poorly (`kernel` 10 of 12 out of reach, `metapackages` 6, `news`
  7), the language and library sections predict well.
- The pipeline on apt's hooks ([`design.md`](design.md)): stage 2 against
  wedging and version skew, stage 3 seeding and shims for the script
  classes above.
- The patch set ([`apt-dpkg-port.md`](apt-dpkg-port.md)): patch A and the
  move to current upstream for finding 4; patch C for the setuid helper;
  patch B not justified by skew.

## Re-running

The survey is re-run after each step of `design.md`'s order of work and
compared per section. The tools used here (sampling, the isolated install
loop in a dsb test account) are to be turned into a bash script under
`dev/`; until then this page records exactly how it was done.
